## 2. コーデックのベンチマーク

連続3回実行の中央値です。アロケーション回数は3回すべてで同一だったため、
中央値ではなく厳密値です。

| ベンチマーク            |   ns/op |     MB/s |        rows/s | allocs/op |
|------------------------|--------:|---------:|--------------:|----------:|
| decode `SELECT 42`     |     156 |    583.1 |     6 408 896 |         5 |
| decode 5k-row BIGINT   |     320 |119 732.4 |15 634 160 641 |         9 |
| decode+values 5k-row   |  16 535 |  2 315.8 |   302 391 158 |         9 |
| decode+flat 5k-row     |   9 142 |  4 188.5 |   546 913 831 |         9 |
| decode VARCHAR         |     252 |    511.4 |     3 972 458 |         7 |
| decode NULL-heavy      |     166 |    784.9 |    60 071 183 |         5 |
| decode STRUCT          |     363 |    477.8 |     2 753 054 |         9 |
| decode MAP             |     509 |    470.5 |     1 965 541 |        13 |
| encode PREPARE request |      20 |  4 446.4 |    49 077 755 |         1 |
| bind 4 parameters      |     142 |    637.6 |     7 038 051 |         1 |

3回の実行間のばらつきは、`decode NULL-heavy` (157〜189 ns、±10 %) を除く全行で
±4 % 以内でした。この項目は実行時間が短く、スケジューラのノイズが支配的になります。

`MB/s` は毎秒デコードしたワイヤバイト数です。`rows/s` はフィクスチャの行数を経過時間で
割った値なので、1行のフィクスチャでは小さく、5,000 行のフィクスチャでは非常に大きくなります。
行をまたいで比較する際は `rows/s` ではなく `ns/op` を見てください。

## 3. アロケーション列の読み方

この表で最も重要なのがこの列です。

**アロケーション回数は行数に比例しません。** `decode SELECT 42` (1 行) は 5 回、
`decode 5k-row BIGINT` (5,000 行) は 9 回です。行数が 5,000 倍になっても
アロケーションは 4 回しか増えません。

理由は、デコーダが大量データのペイロードをコピーせずレスポンスバッファから
**借用 (borrow)** するためです。フラットな `BIGINT` カラムは、確保して 1 行ずつ
埋めるのではなく、既に到着しているバイト列を指すスライスをベクトルが保持します。
したがってアロケーションは結果の*サイズ*ではなく*構造* (カラム数、チャンク数、
入れ子の深さ) に比例します。

呼び出し側にとっての直接的な帰結は生存期間の規則です。借用したデータはチャンクが
解放された時点で無効になり、それは次の `nextChunk()` の時点です。
所有権の規則の全体は [TYPES.md](./TYPES.md) を参照してください。

## 4. 型付き経路と Value 経路の比較

表中の 2 行は*同一*の 5,000 行フィクスチャをデコードし、そこから全値を読み出しています。

| 経路 | ns/op | 相対 |
|------|------:|-----:|
| `decode+flat 5k-row` — `at(T, i)` / `asSlice(T)` | 9 142 | 1.0× |
| `decode+values 5k-row` — `getValue()` → `Value` | 16 535 | 1.8× |

同じ処理に対して型付きアクセサは**約 1.8 倍高速**です。`Value` はタグ付き union なので、
読み出しごとにアロケーションは発生しないものの、型タグに対する switch と union への
コピーのコストを払います。`at(i64, i)` は境界検査とロードにコンパイルされます。

扱いやすさが重要な場面 (型混在カラム、汎用的な表示、CLI) では `Value` を、
スループットが重要な場面では `at`/`asSlice` を使ってください。どちらも正しく、
選択は純粋にコストの問題です。

`asSlice(T)` は成功時にはさらに高速です。レスポンスバッファを参照するスライスを
そのまま返し、値ごとの処理が一切発生しないためです。ペイロードが `T` に対して
アラインメント不正である場合、または格納幅が一致しない場合は `null` を返します。
これは実際には頻繁に起こります — [§8](#8-性能上の落とし穴) を参照してください。

## 5. 入れ子型

| ベンチマーク | ns/op | allocs/op |
|-------------|------:|----------:|
| decode STRUCT | 363 | 9 |
| decode MAP | 509 | 13 |

MAP は**保持するエントリ数に関係なく** 13 回のアロケーションで済みます。
DuckDB が MAP を `LIST(STRUCT(key, value))` として格納し、Quackling がキーと値の
子ベクトルをペアとして実体化せず借用するためです。同じ理屈が STRUCT と LIST にも
当てはまります。

したがって入れ子はアロケーションの観点では低コストで、そのコストはデータ量ではなく
*スキーマ*の関数になります。

## 6. エンドツーエンドのストリーミング

ネットワークを含めた、稼働中の `quack_serve()` インスタンスに対する
ループバック HTTP 経由の測定です。

```sh
zig build -Doptimize=fast
./zig-out/bin/example-streaming
```

```
1000000 rows in 489 chunks, sum = 499999500000
fetches: 41, bytes received: 16024162
        0.49 real         0.10 user         0.02 sys
```

| 指標 | 値 |
|------|-----|
| 行数 | 1,000,000 |
| チャンク数 | 489 |
| FETCH 往復回数 | 41 |
| 受信ワイヤバイト数 | 16,024,162 (約 16 MB) |
| 実時間 | 0.49 秒 |
| ユーザ CPU | 0.10 秒 |

注目すべき点が 2 つあります。第一に、489 チャンクに対して往復は 41 回です。
FETCH レスポンスは複数のチャンクを運ぶため (サーバ既定値は 12、
`compat.default_fetch_batch_chunks` を参照)、往復コストが償却されます。
第二に、実時間 0.49 秒のうちユーザ CPU は 0.10 秒です。このワークロードは
デコードではなく、サーバとソケットの待ち時間が支配的です。

## 7. メモリはバッチサイズで有界

ストリーミングの契約は、ピークメモリが結果全体ではなく**1 つの FETCH バッチ**に
比例することです。各チャンクを保持せずストリームして書き出す CLI で測定しました。

```sh
/usr/bin/time -l ./zig-out/bin/quackling --token … --format csv \
    "SELECT i FROM range($N) t(i)" > /dev/null
```

| 行数 | ピーク RSS |
|-----:|----------:|
| 100,000 | 2.8 MB |
| 1,000,000 | 2.8 MB |
| 5,000,000 | 2.8 MB |

**データ量が 50 倍になってもメモリは増えません。** 一度に常駐するのが厳密に 1 バッチ
だけなので、曲線は劣線形どころか完全に平坦です。

*蓄積する*呼び出し側は当然増加します。`example-streaming` は同じ 1,000,000 行で
6.3 MB がピークになりますが、これは累計値と大きめの出力バッファを保持するためです。
有界性が保証されるのは*ライブラリ*が保持する分であり、アプリケーションが
保持を選んだ分ではありません。

### テストが実際に検証していること

`tests/integration_test.zig` に
`"integration: streaming memory is bounded by batch size, not result size"`
があります。上記の表より弱い検証なので、正確に述べます。

- RSS ではなく**ライブ確保バイト数の高水位**を数えます。テスト内のコメントは
  RSS と時間計測は「テストのゲートにするにはノイズが大きすぎる」と述べています
- 100k/1M/5M ではなく、**10,000 行と 500,000 行**を比較します
- `large < small * 4` のみを検証します。ストリーミングがバッファリングに退行すれば
  明確に失敗する、意図的に緩い上限であり、MB 値を固定するものではありません

つまりテストは*性質*を守り、上記の表は測定値です。どちらも他方の代わりにはなりません。

## 8. 性能上の落とし穴

**`asSlice(T)` が `null` を返すのは例外ではなく通常です。** ワイヤ上のペイロードに
アラインメントの保証はありません。WASM ブリッジ経由の測定では、プレーンな `INTEGER`
カラムのペイロードポインタが `ptr % 4 == 3` (`i32` に対してアラインメント不正) で
返り、*すべての*チャンクでゼロコピー経路が拒否されました。必ずフォールバックを
書いてください。

```zig
if (col.asSlice(i64)) |slice| {
    for (slice) |v| consume(v);          // アラインメントが許せばゼロコピー
} else if (col.isFlat(i64)) {
    for (0..chunk.row_count) |i| consume(col.at(i64, i).?);  // 常に動作する
}
```

`asSlice` を想定経路、フォールバックを稀なケースと考えると、自分のベンチマークを
誤読することになります。

**1 接続につき結果は 1 つです。** 同一接続での 2 つ目のクエリは、1 つ目の結果の
サーバ側カーソルを破棄します。並行性には `Pool` が必要で、1 つのクライアントに
クエリを増やすことでは得られません。インターリーブを試みると、高速化ではなく
`error.ResultSuperseded` が返ります。

**`typed.collect` はストリーミングを無効化します。** 結果全体を実体化するため、
ピークメモリが行数に比例します。さらに進行に伴って各チャンクを解放するので、
収集した構造体の `[]const u8` フィールドは解放済みバッファを指します。
結果が小さく、かつスライス型のフィールドを含まない場合を除き、
`typed.iterator` を使ってください。

**Debug ビルドは参考になりません。** ファズスイート単体で Debug は ReleaseSafe の
約 680 倍遅くなります (約 14 秒 対 約 0.2 秒)。原因は処理量ではなく、
アロケータの簿記処理とインライン化の欠如です。ベンチマークは必ず最適化ビルドで
行ってください。

## 9. ハーネスの仕組み

[`bench/bench.zig`](../../bench/bench.zig) は意図的に小さく作られています。
ベンチマークごとに次を行います。

1. **ウォームアップ。** `min(iters / 10 + 1, 50)` 回の非計測反復を先に実行し、
   初回アクセス時のページフォルトが測定区間に入らないようにします。
2. **アロケーション計数。** `CountingAllocator` が実アロケータをラップして
   全呼び出しを数えるため、`allocs/op` は推定ではなく厳密値です。
3. **時間計測。** `std.Io.Clock.now(.awake, io)` で計測ループを挟むため、
   マシンがスリープしていた時間は除外されます。
4. **デッドコード対策。** 結果を `std.mem.doNotOptimizeAway` に渡すため、
   `ReleaseFast` が測定対象の処理を削除できません。

反復回数はベンチマークごとに設定されており (安価な 1 行デコードは 200,000 回、
5,000 行のものは 1,000〜2,000 回)、各測定が安定する長さになっています。

新しいケースの追加は `bench/bench.zig` に 1 行です。

```zig
try bench(io, allocator, "decode MY CASE", my_fixture, 100_000, decodeFull);
```

## 10. 測定していないこと

本ページの内容が実際より広い主張として読まれないよう、明示します。

- **TLS なし。** すべての測定はループバック上の平文 HTTP です。TLS ハンドシェイクと
  レコード層のコストは本ページのどこにも含まれていません。
- **実ネットワークなし。** ループバックにはパケットロスも、測定に値する RTT も、
  MTU の影響もありません。実回線での挙動を予測できるのは
  往復回数 ([§6](#6-エンドツーエンドのストリーミング)) であり、実時間の数値ではありません。
- **並行性のベンチマークなし。** `Pool` にはマルチスレッド競合テストを含む正当性
  テストがありますが、接続数に対するスループットの測定はありません。
- **単一マシン、単一アーキテクチャ。** Apple `aarch64` のみです。x86-64 での検証は
  なく、WASM ビルドのベンチマークは一切ありません。
- **他クライアントとの比較なし。** DuckDB 純正クライアント、DuckDB-Wasm、その他の
  実装に対する Quackling の測定はありません。
- **サーバ側のコストは対象外。** これらはクライアントを測定した数値です。
  DuckDB 内部のクエリ実行時間は計上していません。
