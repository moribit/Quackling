# Security

[English](../en/SECURITY.md) · **日本語**
→ [ドキュメント目次](./README.md)

Quack サーバは HTTP 越しに SQL 実行を提供する。Quack *クライアント*は、そのサーバ —
あるいはサーバに成りすませる任意のもの — が返してきたバイト列を解析する。本文書は
Quackling が何から守るのか、各防御がどう実装され検証されているのか、そして何を明示的
に対象外とするのかを述べる。

## 脅威モデル

**クライアントはネットワークから信頼できないバイト列を消費する。デコーダ (decoder) が
攻撃面 (attack surface) の全体である。**

Quackling はリクエストを送り、バイト列を受け取る。そのバイト列について興味深いこと
すべて — メッセージ型、field id、長さ接頭辞、要素数、入れ子構造、型タグ、ペイロード幅 —
は相手側が選ぶ。侵害されたサーバ、敵対的プロキシ、平文接続上の経路外攻撃者、あるいは
単にバグのあるサーバが、そこへ任意のバイト列を置ける。

クライアントの脅威モデルでは次を前提とする。

- レスポンス本体は完全に攻撃者の制御下にある。
- HTTP ステータスとヘッダも攻撃者の制御下にある。
- 相手は停滞しうる、ストリームを決して終端しないことがある、長さについて嘘をつきうる。
- SQL テキストは*我々の*呼び出し側が選ぶ。そしてパラメータ値は、その呼び出し側の
  エンドユーザ由来の信頼できない入力かもしれない。

[`../../tests/fuzz_test.zig`](../../tests/fuzz_test.zig) に記された契約 (contract):

> The decoder is the only component that consumes untrusted bytes, so the
> contract it must uphold is narrow and absolute: **arbitrary input produces
> either a successful decode or a typed error — never a panic, an
> out-of-bounds read, an integer overflow, or unbounded allocation.**

ライブラリの構造上の 2 点が、この契約を監査可能にしている。第一に、protocol /
serialization / types 層はバイトスライス上の純粋計算である — ソケットも libc も OS
呼び出しも無い — ので、信頼できないバイト列の扱いはすべて `[]const u8` とテスト用
アロケータ (allocator) だけで到達できるコードに閉じ込められている。第二に、トランス
ポート (transport) は呼び出し側が注入するので、デコーダをネットワーク無しでモックや
ファザ (fuzzer) から駆動できる。

明示的にスコープ*外*のもの: サーバを自身のクライアントから守ること、認可
(authorisation) — Quack には共有トークンが 1 つあるだけでユーザという概念が無い —、
そして呼び出し側が実行を選んだクエリの SQL 意味論に関するあらゆること。

## トークンの取り扱い

認証トークンは **プロトコル本体の内部**を通る。`CONNECTION_REQUEST` のフィールド 1
としてであり、HTTP ヘッダでも URL でもない。フレーミングは
[`../ja/PROTOCOL.md`](./PROTOCOL.md) を参照。

これには避けられない帰結が 1 つある。

> **localhost を超える用途では TLS を使うこと。DuckDB サーバ自身は TLS を終端しない
> ので、前段にリバースプロキシ (reverse proxy) を置くこと。**

トランスポート暗号化が無ければ、トークンはハンドシェイクごとに平文で線上に乗る。
TLS を終端してループバックの `quack_serve()` へ転送するリバースプロキシ (nginx、Caddy、
クラウドのロードバランサ) がサポートされる構成である。`ClientOptions.headers` はこの
ケースのためにも存在する — 認証を要求するプロキシは、Quack トークンに触れずに追加の
HTTP ヘッダで満たせる。

Quackling はトークンをログ出力せず、表示せず、エラーメッセージにも含めない。そもそも
ライブラリ内にログ文が一切無い。可観測性は `Observer` コールバックと `Stats` 構造体を
通るが、どちらにもトークンは渡されない。`Client.lastError()` はサーバ自身のメッセージ
テキストを、そのまま無改変で返す。

これは意図にとどまらずテストで強制されている。
[`../../tests/client_test.zig`](../../tests/client_test.zig) には *"the auth token
never leaks into errors, stats or debug output"* があり、特徴的な秘密文字列で失敗する
ハンドシェイクを駆動し、その秘密が次のいずれにも現れないことを検証する。

| 面 | 検証内容 |
|---|---|
| `client.lastError()` | 秘密が存在しない |
| `client.url` | 秘密が存在しない |
| 書式化した `client.stats` | 秘密が存在しない |
| `mock.sent.items[0]` (ハンドシェイク本体) | 秘密が**存在する** — 積極的に検証 |

最後の行が重要である。このテストはトークンが属する唯一の場所を固定するので、将来の
リファクタリングで送信をやめたり、別の場所へ送り始めたりすれば失敗する。

対になるテスト *"a query error message cannot echo the token"* は、トークンをエラー
文字列の中へ反射して返すサーバをスクリプト化し、そのメッセージが無改変で保持される
ことを検証する。この保証は意図的に厳密である。**我々は決してトークンを何かへ付け加え
ない。サーバを検閲することはしない。** サーバが秘密をエラーテキストへ反射しているなら
それはサーバ側の問題であり、Quackling がそれを黙って隠すことはしない。

運用上の注意:

- トークンは再接続に必要なため、クライアントの生存期間中 `ClientOptions` に保持される。
  `deinit` でゼロ埋めはされない。
- `Pool` は 1 つのトークンをプール内の全接続で共有する。
- 認証失敗は `error.ServerError` とは別の `error.AuthenticationFailed` に分類されるので、
  呼び出し側は文字列照合なしに反応できる。分類はメッセージテキストによる
  (`"authenticat"`、`"invalid token"`、`"unauthorized"`、大文字小文字を無視) —
  サーバが不正トークンを通常のエラーレスポンスとして報告するからである。後述の
  [エラー分類](#プロトコルバージョン交渉) を参照。照合は意図的に狭い。偽陰性は
  `ServerError` に落ちるだけで、それでも正確である。

## メモリ安全性

- **すべてのデコードが境界検査 (bounds check) される。** `Reader.take(n)` は
  `n > remaining()` のとき拒否し、すべてのプリミティブリーダがそこを通る。
  [`../../src/serialization/reader.zig`](../../src/serialization/reader.zig) を参照。
- **ワイヤデータを構造体へ `@ptrCast` することは決してない。** デコード経路のどこにも、
  レスポンスバッファへ重ねた `extern struct` は存在しない。すべてのフィールドは失敗
  しうる関数によって、1 つずつ明示的に読まれる。
- **固定幅の値は明示的なリトルエンディアン (little-endian) 読み出しで読む。**
  `std.mem.readInt(T, bytes[off..][0..@sizeOf(T)], .little)`、浮動小数点は `@bitCast`。
  ゆえにビッグエンディアンのターゲットでもデコードは正しく、ホストのバイト順に依存
  しない。
- **アラインメント (alignment) は前提としない。** Quack のペイロードはバイト詰めで
  あり、含む型に対して一般にアラインされていない。アクセサは 2 つ、契約も 2 つある。

  | アクセサ | 振る舞い |
  |---|---|
  | `Vector.asSlice(T)` | `?[]const T` を返す — ベクタが `T` の平坦な連続であり*かつ*借用バッファが偶然その型に正しくアラインされている (`@intFromPtr(ptr) % @alignOf(T) == 0`) 場合を除き **null**。非 null の結果は最適化として扱い、通常経路とは考えないこと。 |
  | `Vector.at(T, i)` | `T` の平坦な連続に対しては常に動く。`i` を境界検査し、明示的なリトルエンディアン読み出しを行う。アラインメントは無関係。 |
  | `Vector.copySlice(T, out)` | アラインメントが協力しないときの一括代替。呼び出し側所有のメモリへ 1 パスで書く。 |

  `asSlice` が null を返すのは*仕様*である。ミューテーションカタログには
  `vector/asslice-alignment` があり、このアラインメント検査を除去する — そしてスイートは
  それを捕捉する。
- **どちらのアクセサも有効性マスク (validity mask) を参照しない。** `asSlice` と `at` は
  格納されている生の値を返す。NULL の行にもペイロード上には*何らかの*値がある。併せて
  `vector.validity` を確認すること。これは両方の呼び出し箇所に文書化されており、
  メモリ安全性ではなく正しさの罠である。
- **エラー経路もメモリを解放する。** ファズスイートはすべてのデコードを
  `std.testing.allocator` の下で実行し、成功経路・失敗経路の両方で解放するので、不正
  入力経路でのリーク (leak) はテスト失敗になる。入れ子型のエラー経路でのリークは実際に
  この方法で見つかった欠陥である ([検証](#検証) を参照)。

## リソース制限

長さと個数の接頭辞は、設定可能な上限**および**実際に残っているバイト数の**両方**に対し、
**確保 (allocation) の前に**検証される。両方が必要である。設定可能な上限は「大きいが
あり得そうな」主張を止め、残余バイト検査は手元のバッファに対して算術的に不可能な主張を
止める。ゆえに敵対的な長さフィールドが大きな確保を引き起こすことはできない。

| ガード | 場所 | デフォルト値 | 止める攻撃 | 調整方法 |
|---|---|---|---|---|
| `Limits.max_byte_length` | `Reader.readLength` | **256 MiB** (`256 * 1024 * 1024`) | 単一の文字列/BLOB の長さ接頭辞が不合理な大きさを主張する | `Reader.initWithLimits`。`Client` は `max_response_bytes` から導出するので、そちらを下げればこれも下がる |
| 長さ対 `remaining()` | `Reader.readLength` | 該当なし — 常時有効 | 実在するバイト数より大きい長さ接頭辞。確保前に拒否される | 設計上、調整不可 |
| `Limits.max_list_length` | `Reader.readListLength` | **64 Mi 要素** (`64 * 1024 * 1024`) | 各要素が小さくても確保が巨大になるよう、2^32 エントリを主張するリスト/要素数 | `Reader.initWithLimits` |
| 個数対 `remaining()` | `Reader.readListLength` | 該当なし — 常時有効 | 同じ攻撃を逆側から。各要素は最低 1 バイトを消費するので、残余バイト数を超える個数は確実に切り詰められた入力である | 設計上、調整不可 |
| `Limits.max_depth` | `Reader.enterObject` | **64** | 深く入れ子になったメッセージが再帰的な型/ベクタデコーダを通じてスタックを枯渇させる | `Reader.initWithLimits` |
| `Reader.take` の境界 | すべてのプリミティブ読み出し | 該当なし — 常時有効 | バッファ終端を踏み越えるあらゆる読み出し | 設計上、調整不可 |
| `ClientOptions.max_response_bytes` | `Client.roundTrip` | **256 MiB** | 過大なレスポンス本体をそもそもデコードすること。リーダの `max_byte_length` へも伝播する | `ClientOptions` |
| `NativeTransport.Options.max_response_bytes` | `native.sendFn` | **256 MiB** | 1 層下での同じ上限。本体がクライアントへ届く前にトランスポートが拒否する | `NativeTransport.init` |
| `Result.max_fetches` | `Result.fetchNextBatch` | **5,000,000** | ストリーム終端を決して通知しない相手がクライアントを永久に FETCH ループへ留めること | `Result` のフィールドへ代入する |
| `standard_vector_size` 行上限 | `decoder.zig` | **2048** | DuckDB のベクタが保持できる以上の行数を主張するチャンク | フォーマットで固定 |
| `PoolOptions.max_connections` | `Pool.acquire` | **8** | 負荷下での無制限な接続増加。`wait_policy = .fail` なら待たせるのではなく負荷を捨てる | `PoolOptions` |

`max_fetches` について、[`../../src/result.zig`](../../src/result.zig) より:

> End-of-stream is signalled by the *server* sending an empty batch, so a server
> that never does would otherwise loop forever. At the documented batch size
> (12 chunks × 2048 rows) this ceiling still allows well over 10^11 rows, so it
> cannot be reached by legitimate use — it exists purely to keep a broken or
> hostile peer from hanging the caller.

超過すると `error.FetchLimitExceeded` を返し、結果を完了扱いにする。

完全に信頼できないサーバからのレスポンスをデコードするなら、デフォルト値を受け入れる
のではなく締めること。ファズスイート自身の設定は敵対的環境の妥当なモデルである:
`max_byte_length` 1 MiB、`max_list_length` 65536、`max_depth` 32。

## SQL インジェクション境界

**Quack プロトコルバージョン 1 にはパラメータのワイヤ表現が存在しない。**
`PREPARE_REQUEST` はフィールドを厳密に 1 つ — SQL 文字列 — しか運ばず、サーバはそれを
直接 `SendQuery(sql)` へ渡す。稼働中のサーバに対して次の 2 点が検証され、
[`../../src/params.zig`](../../src/params.zig) に記録されている。

- `SELECT ?` は *"Expected 1 parameters, but none were supplied"* を返す — 供給する
  経路が存在しない。
- `PREPARE_REQUEST` へフィールドを追加するとサーバは HTTP 500 を返す — 未知の
  フィールドは拒否されるので、勝手に作ることはできない。

ゆえにパラメータは**クライアント側で** SQL テキストへ埋め込まれ、安全性の負担すべてが
その 1 ファイルに落ちる。ファイルはそれに応じて書かれている。曖昧さなくエンコードでき
ないものは近似せず拒否する。

真のサーバ側プリペアドステートメント (prepared statement) が必要な呼び出し側は、
SQL レベルの `PREPARE` / `EXECUTE` を使える。プロトコルはこれを問題なく扱う。

### `bind()` が強制する規則

| 規則 | 詳細 |
|---|---|
| 引用符エスケープ | テキストパラメータ内の `'` は二重化される (`''`)。`"o'brien"` は `'o''brien'` になる。 |
| 文字列リテラルをスキップ | `'...'` リテラル内の `?` はプレースホルダではなくデータ。`copyQuoted` が二重引用符エスケープを尊重しつつ領域をそのまま複写する。 |
| 引用識別子をスキップ | `"..."` も同様に扱う。 |
| ドル引用文字列をスキップ | `$tag$ ... $tag$` 領域はそのまま複写される。タグに使えるのは英数字と `_` のみ。それ以外ならドル引用ではなかったと判断し、`$` をそのまま複写する。 |
| 行コメントをスキップ | `--` から次の改行 (または入力終端) までをそのまま複写する。 |
| ブロックコメントをスキップ | `/*` から対応する `*/` (または入力終端) までをそのまま複写する。注意: 入れ子には対応しない。 |
| 個数一致を双方向で | プレースホルダが多すぎれば超過時点で `error.ParameterCountMismatch`、少なすぎれば末尾で同じエラー。呼び出し側とクエリは文の形について一致していなければならない。 |
| UTF-8 検証 | `std.unicode.utf8ValidateSlice`。不正な並びは `error.InvalidUtf8` となり、悪いバイト列がサーバ側で予期しない解析を生むことを防ぐ。 |
| NUL 拒否 | テキストパラメータに埋め込まれた `0x00` は `error.UnsupportedParameter` — DuckDB は文字列リテラル内でこれを運べない。 |
| パラメータ集合を制限 | `Param` は意図的に `Value` より小さい。厳密で曖昧さのない SQL リテラル形を持つ variant のみ。損失を伴う型や方言依存の型は推測せず省く。 |
| BLOB は完全に 16 進エスケープ | 全バイトが `'...'::BLOB` 内で `\xHH` になる — 曖昧さがなく、バイナリデータの引用問題に対して免疫がある。 |
| 非有限の double を処理 | NaN/±Inf には素のリテラル形が無いので `'NaN'::DOUBLE` 等になる。有限の double は最短往復形と `::DOUBLE` キャストを使い、DuckDB が DECIMAL と読まないようにする。 |
| エラーは I/O の前に発生 | パラメータエラーは何も送信する前に返る。まさにそれを検証するクライアントテストがある。 |

失敗は送信前に検査されるので、インジェクションの試みは文ではなくリテラルになる。
`"'; DROP TABLE users; --"` は単一の引用文字列として描画される。そのケースの
ユニットテストが `src/params.zig` にあり、稼働サーバに対する
`integration: parameter binding resists SQL injection` テストもある。

### ⚠️ 警告: `.raw_sql`

`Param{ .raw_sql = "..." }` は**一切のエスケープなしに、そのまま**挿入される。値の
位置で式を使えるようにするために存在する — `now()`、列参照、関数呼び出し。

**信頼できない入力から `.raw_sql` の値を構築しては絶対にならない。** そうすることは
直接の SQL インジェクションであり、このライブラリの他のどの検査も捕まえない。個数検査は
これも 1 つとして数えるだけであり、UTF-8 検査と NUL 検査は適用されず、上記のエスケープ
規則はまさにこれが迂回する経路である。文字列がリクエストパラメータ、自分で管理していない
設定ファイル、データベースの列、ファイル名に由来するなら、`.raw_sql` にしてはならない。

動的な識別子 (テーブル名や列名) が必要な場合は、`.raw_sql` の近くへ持ち込む前に、
自分が管理する名前の許可リスト (allow-list) で検証すること。

## エンドポイント検証

[`../../src/uri.zig`](../../src/uri.zig) は `quack:host[:port]` (DuckDB 自身の形式)、
`quack://host[:port]`、および素の `http://` / `https://` URL を受け付ける。検証は
意図的に厳格である。

| 拒否対象 | エラー | 理由 |
|---|---|---|
| 埋め込み資格情報 (authority 部のどこかの `@`) | `error.InvalidUrl` | 黙って捨てられることになる — Quack は URL ではなく本体で認証する。認証済みに*見えて*実はそうでない URL は、エラーより悪い。 |
| ホスト内の制御文字と空白 (`c <= 0x20 or c == 0x7F`) | `error.InvalidUrl` | ヘッダ/リクエストの密輸 (smuggling) や、判読不能なホストが URL へ貼り込まれることを防ぐ。 |
| ポート `0` | `error.InvalidPort` | 実在の宛先ではありえない。通常は解析事故である。 |
| 空のホスト | `error.EmptyHost` | |
| 解析不能 / 範囲外のポート | `error.InvalidPort` | `parseInt(u16)` なので `70000` は切り詰めではなく拒否される。 |

パス、クエリ、フラグメントは捨てられる。エンドポイントのパスはプロトコルで固定
(`/quack`) されているためである。IPv6 リテラルは明示的に扱う — 角括弧形式は解析され、
URL 構築時に再度括弧が付く。素の IPv6 アドレス (コロンが複数あり括弧が無い) は、最後の
グループをポートと誤読するのではなく、ポート無しのホストとして扱う。

検証は `Client.init` で行われるので、不正なエンドポイントは I/O の前に失敗する。それを
検証するクライアントテスト (*"an invalid endpoint fails at init, before any I/O"*) が
あり、各拒否が効いていることを確認する 3 つのミュータント
(`uri/embedded-credentials`、`uri/control-characters`、`uri/zero-port`) もある。

## プロトコルバージョン交渉

クライアントは Quack バージョン 1 を広告し、サポート範囲外のサーバは推測せず拒否する。
[`../../src/protocol/compat.zig`](../../src/protocol/compat.zig) より:

```zig
pub const min_supported_version: u64 = 1;
pub const max_supported_version: u64 = 1;
```

`Client.connect` 内、`CONNECTION_RESPONSE` のデコード後:

```zig
if (body.quack_version < compat.min_supported_version or
    body.quack_version > compat.max_supported_version)
{
    return errors.ProtocolError.UnsupportedProtocolVersion;
}
```

両方の境界が検査される。下限は飾りではない — 下限検査の欠落はミューテーションテストが
見つけた実際の欠陥であり、現在は双方向にそれぞれのミュータント
(`client/protocol-version-min`、`client/protocol-version-max`) がある。Quack はベータ版
であり上流は破壊的変更を予期している。バージョン 2 のチャンクをバージョン 1 として誤読
することは、まさにこの検査が防ぐための失敗である。

ハンドシェイクはセッション ID も要求する。`CONNECTION_RESPONSE` はこれを*ヘッダ*で運び、
空の場合は、接続済みだと思い込んだクライアントを作るのではなく
`error.UnexpectedMessageType` で拒否する。

やり取り全体でのエラー分類:

| 状況 | エラー |
|---|---|
| サーババージョンが `[min, max]` の外 | `error.UnsupportedProtocolVersion` |
| セッション ID の無いハンドシェイク応答 | `error.UnexpectedMessageType` |
| テキストが認証系に見えるハンドシェイクの `ERROR_RESPONSE` | `error.AuthenticationFailed` |
| それ以外のテキストのハンドシェイク `ERROR_RESPONSE` | `error.ServerError` |
| ハンドシェイク応答が来るべき場面での他のメッセージ型 | `error.UnexpectedMessageType` |
| 2xx 以外の HTTP ステータス | `error.HttpError` (デコードを試みない) |
| `max_response_bytes` を超える本体 | `error.ResponseTooLarge` |
| 不正なバイト列 | `SerializationError` のいずれか — `UnexpectedEndOfBuffer`、`VarIntOverflow`、`LengthLimitExceeded`、`UnexpectedFieldId`、`UnexpectedField`、`MalformedVector`、`RowCountTooLarge` |
| 未実装の型やベクタエンコーディング | `error.UnsupportedType` / `error.UnsupportedVectorType` — 決して推測しない |

[`../../src/error.zig`](../../src/error.zig) のエラー集合が*原因*でグループ化されて
いるのは、まさに呼び出し側が「ネットワークが壊れた」「サーバが SQL を拒否した」
「このレスポンスは妥当な Quack ではない」を文字列解析なしに区別できるようにするためで
ある。

## サービス拒否

| 攻撃 | ガード |
|---|---|
| 相手がストリーム終端を通知しない (空バッチを送らない) | `Result.max_fetches` (5,000,000) → `error.FetchLimitExceeded`。*"a server that never signals end-of-stream cannot hang the client"* という名のクライアントテストがあり、ミュータント `result/fetch-ceiling` は**ハングによって**捕捉される — 元の無制限ループが見つかったのもこの経路である。 |
| 巨大な文字列/BLOB を主張する敵対的な長さフィールド | `readLength` における `max_byte_length` **かつ**長さ対 `remaining()`。いずれも確保の前 |
| 巨大な要素数を主張する敵対的な個数フィールド | `readListLength` における `max_list_length` **かつ**個数対 `remaining()`。各要素は最低 1 バイトを消費するので、不可能な個数は即座に拒否される |
| 深い入れ子でスタックを枯渇させるメッセージ | `enterObject` が強制する `max_depth` (64)。ファズスイートは制限 16 に対して 200 段の入れ子 `LogicalType` を流し、スタック死ではなくエラーを要求する |
| 過大なレスポンス本体 | トランスポート層とクライアント層の両方で `max_response_bytes` (256 MiB) → `error.ResponseTooLarge` |
| DuckDB のベクタを超える行数 | `rc > standard_vector_size` (2048) → `error.RowCountTooLarge` |
| 終端しない / 桁溢れする varint | シフトが 64 以上の場合と、ペイロードが対象幅を超える場合に `VarIntOverflow`。この 2 つの側面はそれぞれ別のミュータントでカバーされている |
| 大結果のストリーミング中の無制限なメモリ増加 | 同時に常駐する FETCH バッチは 1 つだけ — 次を要求する前に前のバッチを解放する。実測ピーク RSS: 100 k 行 → 2.6 MB、1 M 行 → 2.7 MB、5 M 行 → 2.9 MB。統合テストがこの上限を検証する |
| 負荷下での接続枯渇 | `PoolOptions.max_connections` (8) と `wait_policy` — `.wait` は待たせ、`.fail` は即座に `error.PoolExhausted` を返すのでリクエストハンドラが負荷を捨てられる |
| 遅い / 停滞した相手 | `ClientOptions.timeout_ms` はトランスポートへ渡され、`CancelToken` はクエリを送信前あるいはストリーム途中で中断できる。**注意:** `NativeTransport` は現在 `timeout_ms` を予約扱いと文書化している — `std.http.Client` がまだ粒度の細かいタイムアウトフックを公開していないため、実際に機能するのは `CancelToken` によるキャンセルである。 |

ガードされて*いない*もの: 制限内で遅く応答する相手、そして正当に巨大な結果を返す
サーバ。どちらも呼び出し側のポリシー判断である — アプリケーションが妥当と考える値に
`max_response_bytes`、`max_fetches`、キャンセルトークンを設定すること。

## 検証

上記の性質はすべて、ファジング (fuzzing)、ミューテーションテスト (mutation testing)、
またはその両方で検証されている。戦略全体は [TESTING.md](./TESTING.md) を参照。
セキュリティに関わる要約:

**ファジング** ([`../../tests/fuzz_test.zig`](../../tests/fuzz_test.zig)) — 3 つの戦略
で 1 回の実行あたり約 25,000 回のデコード。17 フィクスチャのコーパスにおける全
フィクスチャの全接頭辞、全フィクスチャの全バイトを
`0x00/0x01/0x7F/0x80/0xFF` のそれぞれに置換、そして 4000 個の擬似乱数バッファに加えて
手作りの敵対的本体 (2^32 要素を主張するリスト、2^40 バイトを主張する文字列、終端しない
varint、40 段の入れ子オブジェクト)。すべてのデコードはテスト用アロケータの下で走り、
両方の経路で解放するので、エラー経路のリークは実行を失敗させる。
`zig build test --fuzz` は同じエントリポイントを Zig のカバレッジ誘導ファザへ渡す。

**ミューテーションテスト**
([`../../scripts/mutation_test.py`](../../scripts/mutation_test.py)) — 各ガードを 1 つ
ずつ除去し、スイートが失敗することを要求する。その docstring にある論拠: *テストが
通ることはテストが走ったことを証明するだけで、境界検査が消えたときに気づくことは証明
しない。* カタログは **51 ミュータント**で、[リソース制限](#リソース制限) の表の全項目、
[SQL インジェクション境界](#sql-インジェクション境界) の全規則、
[エンドポイント](#エンドポイント検証) の 3 つの拒否、
[バージョン](#プロトコルバージョン交渉) の両境界、FETCH 上限、空バッチによるストリーム
終端、レスポンスサイズ上限、HTTP ステータス検査、セッション ID 要求、有効性マスクの
意味論と境界、`asSlice` のアラインメント検査と長さ検査、そしてプールのロックを網羅する。
ハングは CAUGHT として数える。除去するとスイートが永久に回るガードは、疑いなく効いて
いるからである。現状: **50/50 mutants caught**、加えて文書化された `EXPECTED_SURVIVORS`
エントリ 1 件 (`pool/deinit-waits-for-leases`) — その除去は未定義動作か競合に頼らずには
観測できず、論拠は黙認ではなくスクリプト内に記録されている。これは CI で実行され、
想定外の生存があればビルドを失敗させる。

このプロセスは、テストが緑の陰に隠れていた実際の欠陥を見つけた。

| 欠陥 | 本番でどう失敗したか |
|---|---|
| 無制限の FETCH ループ | 空バッチを送らないサーバがクライアントを永久にハングさせる |
| プールの use-after-free | リースが残っているプールを閉じると使用中の接続が解放される |
| 新クエリで無効化されない結果 | 古い結果が黙って*次の*クエリの行を流す |
| varint のシフト桁溢れ | 不正な長さ接頭辞がエラーではなくパニックを起こす |
| 入れ子型のエラー経路でのリーク | 不正な STRUCT/LIST レスポンスがメモリをリークする |
| 下限バージョン検査の欠落 | サポート範囲を下回るサーバが受理される |

ファジングが実際に何を検証しているかに関わるので、ファズビルドについて注記する。この
スイートは Debug ではなく **ReleaseSafe** でビルドされる。Debug では約 14 秒、最適化
ビルドでは約 0.2 秒かかるからである (約 680 倍。作業量ではなくアロケータの帳簿処理と
インライン化の不在が原因)。ReleaseSafe はファジングが依拠する検査 — 境界、桁溢れ、
`unreachable` — をすべて保持しており、これは元の varint 桁溢れバグを再導入して依然
パニックすることを確認して検証済みである。`-Dfuzz-optimize=Debug` で上書きすれば
Debug レベルの調査ができる。

WASM の FFI 境界は第 2 の信頼できない面として扱われる。JavaScript が生のインデックスと
長さをエクスポートへ直接渡すからである。
[`../../tests/wasm/boundary_test.mjs`](../../tests/wasm/boundary_test.mjs) はすべての
エクスポートを範囲外・敵対的な引数で呼び出す。クエリ前と、さらに重要な事例として実結果
がロードされた状態の両方で行い、何もトラップせず、境界外を読まず、返されたポインタが
線形メモリ内に収まることを要求する。

## 対象外 / スコープ外

率直に述べる。強みだけを並べるセキュリティ文書は役に立たないからである。

- **TLS はテストスイートで実行されていない。** このリポジトリのすべてのテスト、
  ゴールデン取得、統合実行はループバックへの平文 HTTP で行われた。`https` スキームは
  解析され `std.http.Client` へ渡され、`TlsInitializationFailed` 用に `error.TlsError`
  も存在するが、TLS 接続を確立するテストは無い。TLS を終端するプロキシの背後へ配備する
  なら — そうすべきである — 依拠しているのは `std.http.Client` の TLS であって、本
  プロジェクトが検証した何かではない。
- **証明書検証の振る舞いは文書化もテストもされていない。** クライアントはカスタム
  トラストストア、証明書ピンニング、ホスト名検証ポリシー、クライアント証明書のための
  設定を公開していない。`std.http.Client` のデフォルト動作がそのまま起こる。脅威モデル
  が証明書検証の詳細に依存するなら、ビルドに使う Zig のバージョンに対して自分で検証する
  こと。本文書がそれをカバーしていると仮定しないこと。
- **リダイレクトは明示的に扱っていない。** リダイレクト追跡は `std.http.Client` の
  デフォルト動作であり、本プロジェクトが設定するポリシーではない。別ホストへの
  リダイレクトは、本体内のトークンを含むリクエストを、呼び出し側が指定していない場所へ
  運ぶ。それが問題になるなら、リダイレクトしないプロキシをサーバの前段に置くこと。
- **実際の並行負荷における競合は決定的にテストしにくい。** プールにはマルチスレッドの
  競合テスト、「同時に 2 者へ貸し出されない」テスト、並行 acquire/release/discard
  テストがあり、ミューテックスと容量制限のミュータントもある。だがそれは本番負荷下での
  競合 (race) の不在を証明することとは違う。`pool/deinit-waits-for-leases` が
  `EXPECTED_SURVIVORS` に入っているのは、まさにそれが防ぐ不具合が未定義動作か競合を
  介してしか観測できないからである — これは、この種のバグが決定的スイートの到達範囲の
  縁にあるという正直な認めである。
- **統合テストはデフォルトの `test` ステップから外れており、サーバに到達できない
  ときは失敗ではなくスキップする。** サーバ無しでの `zig build test-integration` は
  緑になるが、稼働サーバへの適合性について何も証明しない。それを行うのは実際の DuckDB
  を起動する CI の `integration` ジョブだけである。本プロジェクトをフォークしてその
  ジョブを落とすと、上流のワイヤフォーマット変更を捕まえるレイヤを失う。
- **ゴールデンフィクスチャはスナップショットである。** DuckDB v1.5.5 から取得された。
  Quack はベータ版であり、より新しいサーバは、誰かが再取得するまでコミット済みのバイト
  からは明らかにならない形で異なりうる
  ([ゴールデンフィクスチャの再生成](./TESTING.md#ゴールデンフィクスチャの再生成) 参照)。
- **タイミング攻撃への対策は無い。** トークンの比較はサーバ側で行われ、クライアント側の
  どの処理も定数時間ではない。
- **トークンはメモリから消去されない。** クライアントの生存期間中 `ClientOptions` に
  留まり、`deinit` でゼロ埋めされない。コアダンプやプロセスメモリの読み取りで露出する。
- **`NativeTransport.timeout_ms` は現状 no-op である。** `std.http.Client` が粒度の細かい
  タイムアウトフックを公開していないため予約扱いと文書化されている。DoS 対策として
  頼らないこと。`CancelToken` を使うこと。
- **認可モデルが無い。** Quack には共有トークンが 1 つあるだけで、ユーザ、ロール、
  文単位の権限という概念が無い。トークンを提示できる者は、サーバが実行できる任意の SQL
  を実行できる。サーバ自身に許す操作を制限すること。
- **`.raw_sql` は設計上、防御されていない穴である。**
  [SQL インジェクション境界](#sql-インジェクション境界) の警告を参照。

## 脆弱性の報告

本プロジェクトに専用のセキュリティメーリングリストや公開された開示ポリシーは無い。
脆弱性を見つけた場合は次のようにしてほしい。

- プロジェクトの GitHub リポジトリに issue を開く、またはリポジトリページの連絡先から
  メンテナへ連絡する。
- 機微だと考える問題については、まずそう述べたうえで、初回の報告は簡潔に — 影響を
  示すのに足る程度に — 留め、完全なエクスプロイトを即座に公開しないでほしい。
- 再現手順は非常に助かる。最も有用な形は、それを引き起こすバイト列である。ファズ層と
  デコーダガード層がそれを恒久的な回帰テストとしてそのまま取り込めるからである。
